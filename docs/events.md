# DiscoveryHub — Event Contracts (`docs/events.md`)

This is the source of truth for every Kafka topic and payload in DiscoveryHub.
The record classes in the `common` module
(`com.smarsh.discoveryhub.events.*`) mirror these payloads exactly; if you
change a field here, change the record in the same PR.

**Hard rules, non-negotiable for Day 1 and beyond:**

1. No service reads another service's database, ever. Cross-service state
   change goes through Kafka only; cross-service reads go over REST.
2. Every event carries the **same seven envelope fields** (see below). Producers
   must populate all of them; consumers may rely on them being present.
3. Topic names are versioned (`*.v1`). A breaking change is a new `.v2` topic,
   not an in-place edit.
4. Payloads stay small. Attachment bytes live in S3 — events carry only the
   S3 key (`claim-check` pattern for anything > 512 KB).

---

## 0. The common envelope

Every event is a JSON object with these seven fields at the top level, plus a
`payload` object whose shape is per-topic:

| Field | Type | Meaning |
|---|---|---|
| `eventId` | UUID (string) | Unique id of this event. Generated by the producer; used as the Kafka message value's identity and as the audit entry id. |
| `eventType` | string | The logical event type, e.g. `MESSAGE_INGESTED`, `HOLD_APPLIED`. Stable across versions. |
| `eventVersion` | int | Schema version of this payload, starting at `1`. Bumped on backward-incompatible change. |
| `occurredAt` | ISO-8601 instant (UTC) | When the event happened in the producing domain, not when it was published. |
| `entityId` | string | The primary entity this event is about (`messageId`, `holdId`, `jobId`, `caseId`). Used as the Kafka key unless noted. |
| `correlationId` | string (UUID) | Propagated from the inbound `X-Correlation-Id` header (or generated at the edge). Flows into logs, audit, and downstream events. |
| `actor` | string | Who/what caused the event. From the `X-Actor` header, defaulted to `investigator@demo` (no login on Day 1). |

In the `common` module this is `EventEnvelope<T>`:

```java
public record EventEnvelope<T>(
        UUID eventId,
        int schemaVersion,      // -> eventVersion in JSON
        Instant occurredAt,
        String correlationId,
        String key,             // -> entityId (Kafka key)
        T payload) { }
```

> The Java record names `schemaVersion`/`key`; on the wire we emit
> `eventVersion`/`entityId` to match this contract. A Jackson `@JsonAlias`
> / property-name mapping keeps the two aligned. `eventType` is carried inside
> `payload` so each payload record is self-describing.

## 1. `comm.ingest.v1` — message accepted for ingestion

**Producer:** `ingest-service` (`POST /messages/ingest`).
**Consumers:** `archive-service` (writes Mongo), `search-service` (indexes ES,
own consumer group).
**Key:** `messageKey` (the SHA-256 idempotency digest — deterministic, so a
replay reproduces identical ids).
**Partitions:** 6. **Retention:** 7 d. **DLT:** `comm.ingest.v1.DLT`.

The ingest endpoint **only validates and publishes**. It does **not** write to
Mongo — acceptance and durability are deliberately separate components
(an explicit evaluator question). 202 + `messageId` is returned the instant
the event is acknowledged by Kafka.

```json
{
  "eventId": "8f1c2b3a-...",
  "eventType": "MESSAGE_INGESTED",
  "eventVersion": 1,
  "occurredAt": "2026-09-07T14:02:11Z",
  "entityId": "msg-5f3c91a0",
  "correlationId": "c-4ad1-...",
  "actor": "investigator@demo",
  "payload": {
    "messageId": "msg-5f3c91a0",
    "messageKey": "sha256:9a47...",
    "externalMessageId": "ext-c-0007-th8891-20260314T0912",
    "type": "EMAIL",
    "subject": "Q2 wire instructions",
    "body": "Please process the attached...",
    "threadId": "th-8891",
    "inReplyTo": null,
    "custodianId": "c-0007",
    "participants": [
      { "name": "Ada Byron", "address": "ada@fict.example", "role": "FROM" },
      { "name": "Charlie Babbage", "address": "charlie@fict.example", "role": "TO" }
    ],
    "sentAt": "2026-03-14T09:12:00Z",
    "attachments": [
      { "id": "a-1", "filename": "instructions.pdf",
        "contentType": "application/pdf", "size": 184223,
        "sha256": "f2c1...", "s3Key": "attachments/msg-5f3c91a0/a-1/instructions.pdf" }
    ],
    "hasAttachment": true
  }
}
```

- `messageId` is `UUIDv5(namespace, messageKey)` — deterministic, so a replay
  reproduces identical ids.
- `messageKey = SHA-256(sourceSystem | externalId | canonicalBody |
  sortedParticipants | timestamp)`. The two-guard idempotency
  (`ingest-service` dedupe table + `archive-service` unique index on
  `messageKey`) makes at-least-once delivery safe.
- Attachment **bytes** are never in the event. For payloads < 512 KB the
  generator uploads to a `staging/` S3 prefix and the event carries `s3Key`
  (claim-check); larger attachments are already in S3 by the time this event
  is published.

## 2. `comm.stored.v1` — message durably stored in Mongo

**Producer:** `archive-service`, after the idempotent Mongo upsert + S3
attachment write.
**Consumers:** `search-service` (bulk-index into ES).
**Key:** `messageId`. **Partitions:** 6. **Retention:** **compacted** (so
replaying from offset 0 rebuilds the full ES index — `POST /admin/reindex`).
**DLT:** `comm.stored.v1.DLT`.

```json
{
  "eventId": "b7e2...-...",
  "eventType": "MESSAGE_STORED",
  "eventVersion": 1,
  "occurredAt": "2026-09-07T14:02:13Z",
  "entityId": "msg-5f3c91a0",
  "correlationId": "c-4ad1-...",
  "actor": "archive-service",
  "payload": {
    "messageId": "msg-5f3c91a0",
    "messageKey": "sha256:9a47...",
    "type": "EMAIL",
    "subject": "Q2 wire instructions",
    "body": "Please process the attached...",
    "threadId": "th-8891",
    "custodianId": "c-0007",
    "participants": [ { "name": "Ada Byron", "address": "ada@fict.example", "role": "FROM" } ],
    "sentAt": "2026-03-14T09:12:00Z",
    "hasAttachment": true,
    "onHold": false,
    "holds": [],
    "ingestedAt": "2026-09-07T14:02:13Z",
    "retentionDueAt": "2033-03-14T09:12:00Z"
  }
}
```

- `onHold`/`holds` are included so `search-service` can index the hold state
  without re-reading Mongo; `holds` (the set of hold ids) is the source of
  truth and `onHold = holds.length > 0` is derived.

## 3. `hold.commands.v1` — place / release a hold (command)

**Producer:** `hold-service` (transactional outbox: hold row + outbox row in
one Postgres tx — D-003 moved this ownership out of `case-service`).
**Consumer:** `archive-service` (the hold-applier, `archive-hold-applier` group).
**Key:** `holdId`. **Partitions:** 3. **Retention:** 7 d.
**DLT:** `hold.commands.v1.DLT`.

A hold is a **command**, not a synchronous write, because the scope can cover
the entire corpus. `POST /api/holds` returns 202 + `holdId` with
`status: PENDING` immediately.

```json
{
  "eventId": "1a09...-...",
  "eventType": "HOLD_COMMAND",
  "eventVersion": 1,
  "occurredAt": "2026-09-07T15:10:00Z",
  "entityId": "h-1001",
  "correlationId": "c-7f12-...",
  "actor": "investigator@demo",
  "payload": {
    "holdId": "h-1001",
    "caseId": "case-42",
    "action": "PLACE",
    "scope": {
      "custodians": ["c-0007", "c-0012"],
      "from": "2026-01-01T00:00:00Z",
      "to": "2026-06-30T23:59:59Z",
      "terms": "wire transfer"
    },
    "placedBy": "investigator@demo"
  }
}
```

- `action` is `PLACE` or `RELEASE`. `RELEASE` carries the same `holdId` and
  scope is omitted (the applier already knows it from the hold row).
- The applier resolves the scope to message ids (calls
  `search-service /search/scope-ids`, PIT-paged), does a Mongo
  `$addToSet {holds: holdId}` + `$set {onHold: true}` per batch, then emits
  `hold.applied.v1` per batch, `completed: true` on the final batch.

## 4. `hold.applied.v1` — hold applied to a batch of messages

**Producer:** `archive-service` (hold-applier). **Consumers:** `search-service`
(updates ES `holds`/`onHold`), `hold-service` (`hold-tracker` group — updates
`heldCount`/`status`; this moved from `case-service` with the rest of hold
ownership, D-003).
**Key:** `holdId`. **Partitions:** 3. **Retention:** 7 d.
**DLT:** `hold.applied.v1.DLT`.

```json
{
  "eventId": "c3d4...-...",
  "eventType": "HOLD_APPLIED",
  "eventVersion": 1,
  "occurredAt": "2026-09-07T15:10:09Z",
  "entityId": "h-1001",
  "correlationId": "c-7f12-...",
  "actor": "archive-service",
  "payload": {
    "holdId": "h-1001",
    "caseId": "case-42",
    "action": "PLACE",
    "messageIds": ["msg-5f3c91a0", "msg-9b2e...", "msg-7c1f..."],
    "onHold": true,
    "completed": false,
    "progressPct": 23
  }
}
```

- `completed: true` + `progressPct: 100` on the final batch tells
  `hold-service` to flip the hold to `ACTIVE` (PLACE) or `RELEASED` (RELEASE)
  and set `heldCount`.
- For `RELEASE`: `action: "RELEASE"`, `onHold` reflects whether the message's
  hold set is now empty (true if still held by another overlapping hold,
  false if fully released). **Release removes one hold id; protection ends
  only when the set empties** — never a boolean as the source of truth.

## 5. `case.closed.v1` — a case moved to CLOSED

**Producer:** `case-service` (transactional outbox, same pattern as
`hold.commands.v1`). **Consumer:** `hold-service` (`hold-case-closed` group).
**Key:** `caseId`. **Partitions:** 3. **Retention:** 7 d.

Closing a case is FR-2.5 (`CLOSED` ⇒ read-only) on the case-service side and
FR-4.5 ("releasing a hold when a case closes") on the hold-service side — two
different services' business rules triggered by one fact, which is exactly
what an event (not a synchronous call from case-service into hold-service)
is for.

```json
{
  "eventId": "e5a1...-...",
  "eventType": "CASE_CLOSED",
  "eventVersion": 1,
  "occurredAt": "2026-09-09T15:10:00Z",
  "entityId": "case-42",
  "correlationId": "c-7f12-...",
  "actor": "investigator@demo",
  "payload": { "caseId": "case-42", "closedAt": "2026-09-09T15:10:00Z", "actor": "investigator@demo" }
}
```

- On receipt, `hold-service` finds every hold on `caseId` with status
  `PENDING`/`ACTIVE`/`FAILED` and releases each one (same `RELEASING` →
  outbox `RELEASE` → applier → `hold-tracker` → `RELEASED` path as a manual
  release). A `caseId` with no holds, or an already-unparsable/malformed
  payload, is a no-op — this consumer never throws for a case with nothing
  to release.

## 6. `export.jobs.v1` — export job lifecycle

**Producer:** `export-service` (`POST /exports` -> `QUEUED`; worker ->
`RUNNING`/`COMPLETED`/`FAILED`). **Consumer:** `export-service` worker (own
consumer group, so the request handler and the worker are decoupled).
**Key:** `jobId` (the idempotency key — a redelivered message never yields two
packages). **Partitions:** 3. **Retention:** 7 d. **DLT:** `export.jobs.v1.DLT`.

```json
{
  "eventId": "e5f6...-...",
  "eventType": "EXPORT_REQUESTED",
  "eventVersion": 1,
  "occurredAt": "2026-09-07T16:30:00Z",
  "entityId": "job-2026-09-07-0001",
  "correlationId": "c-9a01-...",
  "actor": "investigator@demo",
  "payload": {
    "jobId": "job-2026-09-07-0001",
    "caseId": "case-42",
    "holdId": null,
    "status": "QUEUED",
    "progressPct": 0,
    "packageS3Key": null
  }
}
```

Lifecycle `status` values: `QUEUED` -> `RUNNING` (`progressPct` 1..99) ->
`COMPLETED` (`packageS3Key` set) or `FAILED` (`error` set). Each transition is
its own event with `eventType` `EXPORT_RUNNING` / `EXPORT_COMPLETED` /
`EXPORT_FAILED`. The `EXPORT_DOWNLOADED` audit event (when the pre-signed URL
is minted) is on `audit.events.v1`, not here.

## 7. `audit.events.v1` — append-only audit trail

**Producers:** every service, emitted inside the same logical operation as the
change it records. **Consumer:** `audit-service` (the only consumer; writes
to Mongo `audit_events`, append-only — the service exposes no write API).
**Key:** `caseId` (so a per-case hash chain is contiguous on one partition).
**Partitions:** 3. **Retention:** 30 d. **DLT:** `audit.events.v1.DLT`.

```json
{
  "eventId": "f7a8...-...",
  "eventType": "AUDIT_EVENT",
  "eventVersion": 1,
  "occurredAt": "2026-09-07T15:10:00Z",
  "entityId": "case-42",
  "correlationId": "c-7f12-...",
  "actor": "investigator@demo",
  "payload": {
    "eventId": "f7a8...-...",
    "occurredAt": "2026-09-07T15:10:00Z",
    "actor": "investigator@demo",
    "action": "HOLD_PLACED",
    "targetType": "HOLD",
    "targetId": "h-1001",
    "caseId": "case-42",
    "before": null,
    "after": "{ \"holdId\": \"h-1001\", \"status\": \"PENDING\" }",
    "correlationId": "c-7f12-...",
    "previousHash": "a1b2c3...",
    "currentHash": "d4e5f6..."
  }
}
```

- `currentHash = SHA-256(previousHash + canonicalJson(payload))` forms a
  per-case hash chain; `GET /audit/verify-chain?caseId=` re-walks it. Silent
  tampering at the DB level is detectable because the chain breaks.
- `action` vocabulary: `CASE_CREATED/UPDATED/TRANSITIONED`,
  `CUSTODIAN_ADDED/REMOVED`, `EVIDENCE_ADDED/REMOVED`,
  `HOLD_PLACED/APPLIED/RELEASED`, `SEARCH_EXECUTED`,
  `EXPORT_REQUESTED/COMPLETED/FAILED/DOWNLOADED`,
  `DISPOSITION_RUN`, `DELETE_BLOCKED_ON_HOLD`.
- The Mongo user for `audit-service` is granted `insert`+`find` only (no
  `update`/`remove`) — append-only is **structural, not policy**.

## Consumer groups (documented, non-negotiable)

Each consumer runs in its **own group** so independent services don't steal
each other's offsets (the Day-1 hard gate checks this explicitly):

| Consumer | Group id | Topics |
|---|---|---|
| `archive-service` ingest consumer | `archive-ingest` | `comm.ingest.v1` |
| `archive-service` hold applier | `archive-hold-applier` | `hold.commands.v1` |
| `search-service` indexer | `search-indexer` | `comm.ingest.v1`, `hold.applied.v1` |
| `hold-service` hold tracker | `hold-tracker` | `hold.applied.v1` |
| `hold-service` case-closed consumer | `hold-case-closed` | `case.closed.v1` |
| `export-service` worker | `export-worker` | `export.jobs.v1` |
| `audit-service` sink | `audit-sink` | `audit.events.v1` |

> Note: `search-service` consumes `comm.ingest.v1` (Day 1 minimal path:
> index directly from the ingest event) **and** will consume
> `comm.stored.v1` once the archive path is wired (Day 2). On Day 1 the
> indexer reads `comm.ingest.v1` in its own `search-indexer` group so it
> does not compete with `archive-ingest`.
